# Задача 2. Кабинет продавца и управление товарами

## Идея

В MarketFlow используется один тип аккаунта пользователя, но у него может быть
несколько ролей. При регистрации человек выбирает, кем он хочет быть:
покупателем или продавцом.

- Покупатель получает роль `BUYER`.
- Продавец получает две роли: `BUYER` и `SELLER`.
- Продавцу не создаётся второй аккаунт.
- Продавец может переключаться между интерфейсом продавца и интерфейсом
  покупателя, не выходя из аккаунта.
- Переключение интерфейса не изменяет роли пользователя и не создаёт новую
  сессию. Меняется только открываемая страница.

На странице регистрации две кнопки отправляют параметр:

```text
accountType=BUYER
accountType=SELLER
```

Backend регистрации должен проверить значение `accountType`. Пользователь не
должен иметь возможность самостоятельно назначить себе `ADMIN`, `OWNER` или
другую служебную роль.

## Интерфейс продавца

Главная страница продавца должна показывать:

- количество активных товаров;
- товары с нулевым или низким остатком;
- последние добавленные товары;
- количество заказов и продаж;
- доход продавца;
- кнопки «Добавить товар», «Мои товары», «Заказы», «Финансы»;
- кнопку «Перейти в режим покупателя».

Каталог продавца показывает только принадлежащие ему товары. Для каждого товара
отображаются изображение, название, цена, количество, активность и основные
показатели продаж. При открытии товара продавец видит полную информацию и может
изменить товар, пополнить остаток, включить или отключить его.

## Пополнение остатка

Продавец может докупить дополнительные единицы своего товара. На первом этапе
остаток можно увеличивать без финансовой операции. После реализации финансов
пополнение должно выполняться в одной транзакции:

1. Проверить роль продавца и принадлежность товара.
2. Проверить количество пополнения.
3. Рассчитать себестоимость.
4. Проверить баланс продавца.
5. Списать деньги продавца.
6. Зачислить деньги платформе.
7. Увеличить остаток товара.
8. Сохранить финансовую операцию и движение остатка.

Для учебной версии себестоимость может составлять 50% цены покупателя. В более
правильной модели её следует хранить отдельно в поле `cost_price`, чтобы
изменение розничной цены не меняло себестоимость автоматически.

## Что создать

```text
controller/SellerDashboardController.java
controller/SellerProductController.java
service/SellerProductService.java
products/CreateProductRequest.java
products/UpdateProductRequest.java
products/RestockProductRequest.java
products/SellerProductDto.java
exception/ProductAccessDeniedException.java
exception/InsufficientSellerFundsException.java
```

Также потребуется:

- добавить `accountType` в DTO регистрации;
- назначать роли в `AuthService`;
- находить товары по `sellerId` в `ProductRepository`;
- переименовать неясное поле продавца в `ProductEntity` в `sellerId`;
- проверять роль продавца и принадлежность товара в Service;
- позднее добавить историю финансовых операций и движений остатка.

## Endpoint-ы регистрации и переключения режима

| Метод и путь | Для чего нужен |
|---|---|
| `GET /register` | Показать общую форму регистрации с выбором покупателя или продавца. |
| `POST /register` | Создать пользователя и назначить роль по `accountType`. Продавцу назначить `BUYER` и `SELLER`. |
| `GET /seller/dashboard` | Открыть главный кабинет продавца со сводной информацией. |
| `GET /account/catalog` | Уже существующий каталог покупателя. Кнопка «Режим покупателя» ведёт прямо сюда; отдельный endpoint переключения не нужен. |

## Endpoint-ы товаров продавца

| Метод и путь | Для чего нужен |
|---|---|
| `GET /seller/products` | Показать только товары текущего продавца. |
| `GET /seller/products/new` | Показать форму добавления нового товара. |
| `POST /seller/products` | Проверить форму и создать товар, указав текущего пользователя как продавца. |
| `GET /seller/products/{productId}` | Показать полную информацию о принадлежащем продавцу товаре. |
| `GET /seller/products/{productId}/edit` | Показать форму редактирования товара. |
| `POST /seller/products/{productId}/edit` | Изменить название, описание, цену, изображение и другие разрешённые поля. |
| `POST /seller/products/{productId}/restock` | Увеличить остаток товара; позднее также списывать стоимость пополнения. |
| `POST /seller/products/{productId}/disable` | Скрыть товар из каталога покупателя, сохранив его и историю заказов. |
| `POST /seller/products/{productId}/enable` | Снова сделать товар доступным в каталоге при наличии остатка. |

## Endpoint-ы заказов, финансов и аналитики продавца

Эти endpoint-ы реализуются после создания заказов и финансовой модели:

| Метод и путь | Для чего нужен |
|---|---|
| `GET /seller/orders` | Показать заказы, содержащие товары текущего продавца. |
| `GET /seller/orders/{orderId}` | Показать состав и состояние конкретного заказа продавца. |
| `POST /seller/orders/{orderId}/status` | Изменить разрешённый продавцу этап обработки заказа. |
| `GET /seller/finance` | Показать баланс, поступления, комиссии и расходы на пополнение. |
| `GET /seller/analytics` | Показать продажи, выручку, популярные товары и остатки за выбранный период. |

## Бизнес-правила

- Только пользователь с ролью `SELLER` может открывать `/seller/**`.
- Продавец может читать и изменять только собственные товары.
- `sellerId` берётся из текущей сессии или Spring Security, а не из HTML-формы.
- Цена и себестоимость должны быть больше нуля.
- Количество товара и количество пополнения не могут быть отрицательными.
- Отключённый товар не показывается в каталоге покупателя.
- Товар с нулевым остатком нельзя положить в корзину.
- Физическое удаление товара заменяется на `active = false`.
- Изменение остатка и списание денег позднее выполняются в одной транзакции.
- Backend не доверяет переданным из браузера ролям, `sellerId`, цене списания и итоговой сумме.

```text

InvalidQuantityException          -> 400
ProductUnavailableException       -> 409
InsufficientSellerFundsException  -> 409
```

## Рекомендуемый порядок реализации

1. Добавить выбор типа аккаунта в backend регистрации и назначение ролей.
2. Создать кабинет продавца и проверку роли `SELLER`.
3. Реализовать список и карточку собственных товаров.
4. Реализовать создание и редактирование товара.
5. Реализовать включение и отключение товара.
6. Реализовать простое пополнение остатка.
7. После финансовой подсистемы добавить платное пополнение.
8. После системы заказов добавить заказы и аналитику продавца.
